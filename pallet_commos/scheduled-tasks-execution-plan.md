# Long-Running / Scheduled Agent Tasks — Execution Plan

## Context

The product requirement is to let a user ask the agent, conversationally, to schedule a recurring or one-off long-running task (e.g. "every Friday, create a PO for fruits and vegetables based on stock and this week's sales"; "review today's new products, verify images/descriptions, and approve them"), have it execute automatically on schedule, track its execution status/history, notify the user, and support pause/cancel — all without hard-coding each new use case into the system.

This repo (`pallet-comms-agent`) is a Java 21 / Spring Boot 4 service using Google ADK for agent orchestration: a `CoordinatorAgent` routes conversational turns to ~20 domain sub-agents/tools (`ProductTool`, `PurchaseAgent`, `CampaignTool`, etc., in `agents/` and `tools/`). It already has a **static** Quartz scheduler (`scheduler/AutopilotScheduler.java`) running 3 hardcoded cron jobs (`scheduler/jobs/ProposalGenerationJob.java`, `SeoAuditJob.java`, `BudgetOptimizationJob.java`), and an `AgentSession`/`AgentSessionStatus` entity that models single-run execution state — a close precedent, but those jobs are compiled-in, org-agnostic loops, not user-defined, pausable/cancellable, per-tenant schedules. There is no notification-sending code in this repo today, and no production UI here (a separate frontend repo consumes `/api/agent/*`).

A requirements review (see "Decisions Made" below) resolved the architecture-shaping ambiguities. This document is the resulting execution plan: phased, with concrete schemas, API contracts, and file-level scope, intended for team review before implementation starts.

## Decisions Made

1. **Scope**: Backend + API only. This repo builds the data model, scheduling engine, conversational creation, and REST endpoints. The production UI is a separate team's work against these endpoints.
2. **Notifications**: A separate notification service already exists (its API contract is still being created by that team). This repo adds a `NotificationAgent` sub-agent + `NotificationTool` that calls that service's API — same tool pattern as `ProductTool`/`CampaignTool`, not a new Pub/Sub topic. **This integration is intentionally open-ended and never a release gate**: every other phase (1–4, 6, 7) calls notification send-points through a stub that logs instead of delivering, so the full system — including testing — is releasable and independently verifiable without `NotificationAgent`/`NotificationTool` being finished. The sub-agent can be swapped in at any later point, including after Phase 7 testing has already completed.
3. **Task representation**: **Hybrid**. Default path — the scheduled task stores the user's natural-language instruction, replayed through the existing `CoordinatorAgent`/`AgentRunner` at trigger time (zero new code for most future use cases). Escape hatch — a task can optionally be backed by a typed `ScheduledTaskHandler` when a use case needs deterministic, tightly controlled logic (e.g. financial actions).
4. **Autonomy**: Configurable per task — `AUTONOMOUS` (executes and notifies after) or `APPROVAL_REQUIRED` (produces a draft/summary and waits for explicit user approval before committing side effects), captured during conversational creation.
5. **Missed runs / errors**: Always notify the user — a missed run (skipped per catch-up policy) or an execution error is never silent.
6. **Circuit breaker**: A task auto-pauses after 3 consecutive failed runs, with a notification explaining why.
7. **Cancellation**: Soft-delete — the `ScheduledTask` row and its run history are retained with status `CANCELLED`, not physically deleted. No un-cancel; a new task must be created.
8. **Ownership enforcement**: This service defensively checks that the requesting `userId` matches the task's owning `userId` on pause/resume/cancel/view calls, rather than trusting the caller.
9. **Missed-run/catch-up**: If a scheduled time is missed (e.g. app was down), skip to the next occurrence rather than firing late — avoids stale side effects like a late PO — and notify the user per decision #5.
10. **Token exhaustion**: If the org/user has run out of available AI tokens, the user is always notified — never silent. Checked both ways: *proactively*, the dispatcher queries the business service (`AiUsageClient.getOrgTokenDetails`) before dispatching a due task and skips the run with a `TOKENS_EXHAUSTED` notification if already exhausted; *reactively*, as a safety net, an exhaustion signal surfaced mid-run from the business service is caught and notified the same way. A proactive skip does not count against the task's `consecutiveFailureCount` (decision #6) — it's an account-level condition, not a task health problem.
11. **Configurable approval flow**: Beyond the binary `autonomyMode` (decision #4), a task can be created with a conditional approval rule — a natural-language threshold captured at creation time (e.g. "only ask for approval if the PO total exceeds $500"). This is stored as `approvalConfig.thresholdDescription` and folded into the replayed instruction context at run time, so the agent itself decides via the existing approval-request mechanism whether that specific run needs sign-off — consistent with the hybrid, zero-new-code-per-use-case philosophy (decision #3), and carrying the same LLM-judgment risk already accepted for cron-phrase parsing (see Risks).
12. **Maximum task duration**: Each task has a `maxDurationMinutes` (falls back to a global default) enforced by the dispatcher. If exceeded, the run is terminated best-effort — marked `TIMED_OUT` and the user notified immediately — and it counts toward the circuit breaker (decision #6), unlike a token-exhaustion skip. "Terminated" is best-effort because `AgentRunner.execute(...)` is synchronous with no cancellation hook today; see Risks for the implication.
13. **Trial-run / prediction**: Always optional, never required to create or activate a task. Once a task has real run history, an estimate is just the historical average of `totalTokens`/`durationMs` already captured per run (free, no execution). For a brand-new task with no history, a trial-run actually executes once — reusing the same "run to draft, don't commit side effects" mechanism as `APPROVAL_REQUIRED`/`CONDITIONAL` (decisions #4, #11, Phase 6) — and the real measured tokens/duration both answer the request and seed the task's first history data point. Available both as an offered step during conversational creation and as a standing on-demand tool/endpoint afterward. The resulting `ScheduledTaskRun` row is flagged `isTrialRun = true` so it's excluded from circuit-breaker counting (decision #6) and from the "due tasks" dispatch query.
14. **Task output in Blob Storage**: Every run's full output text (`AgentResult.response` for the NL path, the handler's result for the typed-handler path) is uploaded to GCS — reusing the existing `GcsUploadService`/`GcsSignedUrlService` signed-URL pattern already used for chart/Excel artifacts — and is retrievable on demand via a signed-URL endpoint, ownership-checked the same as decision #8. `scheduled_task_run` stores the GCS **object reference**, not a signed URL (signed URLs expire per `GcsSignedUrlService`'s configured TTL); the retrieval endpoint mints a fresh short-lived signed URL from that reference on each request. GCS is the **single retrieval path** for scheduled-task output — used uniformly whether the run went through the NL path (which happens to also leave a copy on the pre-existing `AgentSession.finalResponse`) or a typed handler (which has no `AgentSession` at all), so `GET .../runs/{runId}/output` never has to branch its logic per execution path. `AgentSession.finalResponse` is not read for this feature; it continues to exist only for its own unrelated (chat-history) purposes.
15. **Predefined task templates**: Beyond the free-form NL path (decision #3), a task can also be created from a predefined template — a per-org catalog of NL instruction templates with fill-in placeholders (e.g. "Weekly PO for {category} every {day}"). A template-sourced task still executes through the exact same NL-replay path as any free-form task (decision #3's default) — there's no new execution mechanism, just a faster, more guided route to producing the final `instructionText`. Once resolved, a template-sourced task is indistinguishable from a free-form one at run time.
16. **Template catalog ownership & exposure**: Templates are per-org configurable, not hardcoded — stored in a new `scheduled_task_template` table and manageable via REST CRUD (consumed by the separate frontend's template-management UI, per decision #1's backend-only scope). The catalog is exposed both conversationally (the agent can offer/list templates when a user wants to schedule something without a specific instruction in mind) and via `GET /api/agent/scheduled-tasks/templates` for a frontend picker. Access is checked at the `orgId` level (any user in the org can browse/select), a coarser grain than decision #8's per-`userId` checks on tasks — whether template *management* (create/edit/archive) should be further role-gated within an org is not decided (see Risks).

## Remaining External Dependency

**Notification service API contract** is the one unresolved external dependency — endpoint, auth mechanism, and supported channels are still being defined by that service's owning team. `NotificationTool`/`NotificationAgent` can be scaffolded (interface, call sites, config field) in Phase 5 but not finalized until that contract lands. See decision #2 for why this doesn't block the rest of the plan.

### How template-sourced tasks connect to `scheduled_task`

- `scheduled_task.sourceTemplateId` records provenance only. By the time a task is persisted, `instructionText` already has every placeholder resolved into a fixed snapshot, so a template-sourced task is executed identically to a free-form one (decision #15) — the dispatcher (Phase 2) never looks at `sourceTemplateId`.
- Editing or archiving a `scheduled_task_template` never retroactively affects tasks already created from it, for the same reason.

### How this connects to existing session/chat tables

- The **prompt/instruction** is stored exactly once, on `scheduled_task.instructionText` — the single source of truth for "what to run." It is not duplicated onto `scheduled_task_run`.
- To know whether a given execution **is a scheduled task** (as opposed to a live chat turn), reuse the existing `AgentSession.triggerSource` field (already in the codebase, currently populated with values like `"manual"`, `"autopilot_proposals"`). The dispatcher sets `triggerSource = "scheduled_task"` when it calls `AgentRunner.execute(...)` for the NL-instruction path — no schema change needed on `AgentSession`, just a new value for an existing column.
- `scheduled_task_run.agentSessionId` is the join key from a run back to that `AgentSession` row, so a given session's scheduled-task origin — and which task it belongs to — can be resolved either via `AgentSession.triggerSource = 'scheduled_task'` alone, or precisely via `scheduled_task_run.agentSessionId → scheduled_task_run.scheduledTaskId`.
- For the typed-handler path (no `AgentSession` is produced), `scheduled_task_run.handlerResultSummary` is the equivalent execution record — there's no ambiguity to resolve there, since a typed-handler run only ever originates from a scheduled task.
- `AgentSession.finalResponse` and `scheduled_task_run.outputRef` end up holding the same text for NL-path runs — this is intentional, not accidental duplication (decision #14): `outputRef`/GCS is the one retrieval path the output endpoint always serves from, so it behaves the same for NL-path and typed-handler runs alike. Nothing in this feature reads `AgentSession.finalResponse`.

**Reused the existing `[AWAITING_INPUT]` mechanism instead of inventing a parallel one — but had to extend it to reach `executeCoordinator` for the first time.** MarketingAgent's INTERACTIVE MODE and `AgentRunner.rebuildWithTools` already establish a convention: a response prefixed with `[AWAITING_INPUT]` sets `AgentSessionStatus.AWAITING_INPUT`, and a later turn resumes via `AgentRunner.continueSession`. That machinery only ever reached `agentsByType`-registered specialists (`runFromSession`'s MCP path) — `executeCoordinator` (Phase 2's coordinator-tree path, which is what scheduled tasks actually run through) neither detected the marker nor had any resume method, since `TokenTrackingAgentFactory` copies `coordinatorAgent`'s `globalInstruction()` verbatim rather than appending the awaiting-input rule the way `rebuildWithTools` does for the MCP path. Fixed by refactoring `executeCoordinator` into a shared `executeCoordinatorInternal(...)`, which now (a) detects the `[AWAITING_INPUT]` prefix and sets `AgentSessionStatus.AWAITING_INPUT` exactly like `runFromSession` does, and (b) accepts an optional `extraInstructionBlock` inserted into the per-call prompt — the mechanism the dispatcher uses to fold in the draft-mode rule for just this one call, without touching the agent's own globalInstruction (which would affect every other caller of `coordinatorAgent`, live chat included). A new `AgentRunner.continueCoordinatorSession(parentSession, orgId, locationId, userId, replyMessage)` is the coordinator-tree analogue of `continueSession` — it reuses the already-private `buildConversationHistory` to replay prior turns as text (an `InMemoryRunner` carries no cross-turn state of its own), since `continueSession` itself can't be reused as-is: it resolves the agent via `agentsByType.get(AgentType.valueOf(...))`, which is empty for `AgentType.COORDINATOR` by design (see `AgentType.COORDINATOR`'s own javadoc from Phase 2).

**The draft-mode instruction is prompt-only, not tool-gated — same trust model as tenant scoping and cron parsing, now extended to "don't commit yet."** `ScheduledTaskDispatcherJob.approvalInstructionBlock(task)` tells the agent, in the per-call prompt, to prepare the action as a DRAFT/PENDING-APPROVAL using the domain's own draft-capable operation (PO/PI/product flows already model `DRAFT`/`PENDING_APPROVAL` states per `PurchaseAgent`'s schema notes) and withhold any finalize/submit/approve tool call until told to proceed — then emit `[AWAITING_INPUT]` if and only if it stopped short. There is no server-side check that the agent actually refrained from committing; a model that ignores the instruction and commits anyway (without the marker) would be recorded as a normal `COMPLETED` run. This is the same class of risk already flagged for cron-phrase parsing and the conditional-approval threshold (see Risks) — not a new category, but APPROVAL_REQUIRED/CONDITIONAL raise the stakes further since the entire feature exists specifically to prevent unattended commits.

**Extracted `ScheduledTaskRunCompleter` out of the dispatcher so approve/reject can reuse the exact same completion logic.** Approving or rejecting a draft needs to advance `nextRunAt`, reset/increment `consecutiveFailureCount`, run the circuit breaker, and notify — precisely what Phase 2's `onSuccess`/`onFailure`/`onTimeout` already did, just triggered by a conversational tool call instead of the Quartz poll. Rather than duplicate that logic in a new service, it was lifted into `scheduler/ScheduledTaskRunCompleter.java` (`complete`/`fail`/`timeout`/`awaitingApproval`/`reject`/`advanceOrComplete`), and `ScheduledTaskDispatcherJob` now delegates to it. `ScheduledTaskDispatcherJobTest`'s existing assertions needed no behavioral changes — only its constructor call, since `ScheduledTaskRunCompleter` is instantiated directly in the test against the same mocked repositories/notifier it already had.

**New `ScheduledTaskApprovalService`** (`service/ScheduledTaskApprovalService.java`) — `approve(taskId, runId, userId, optionalReplyMessage)` loads the `AWAITING_APPROVAL` run's linked `AgentSession` (ownership-checked via the existing `ScheduledTaskService.getOwnedTask`, decision #8) and calls `continueCoordinatorSession`; the result can land `COMPLETED`, `FAILED`, or back at `AWAITING_APPROVAL` (a further question, or a `CONDITIONAL` rule firing again) — all three are handled via the completer. `reject(taskId, runId, userId, reason)` never touches `AgentRunner` — it resolves the run as `CANCELLED` and still advances the schedule, matching decision #7's soft-delete precedent (nothing is undone, a rejected draft just never became real). Token accounting adds the continuation call's tokens to the draft's already-recorded tokens rather than overwriting, so a run's final `totalTokens` reflects the full cost across both turns.

**Typed-handler approval is out of scope — same reasoning as Phase 2 leaving the handler registry empty.** `ScheduledTaskHandler.execute(task, draftOnly)` already had the `draftOnly`/`requiresApproval` shape from Phase 2, and the dispatcher now passes `draftOnly = autonomyMode != AUTONOMOUS`; but resuming a typed-handler draft has no `AgentSession` to continue from, and no handler exists yet to design a resume contract against. `ScheduledTaskApprovalService.approve` throws `AgentServiceException.unsupported(...)` when `run.getAgentSessionId() == null` (the typed-handler signal) rather than guessing at a mechanism with nothing concrete to validate it.

**New tools/routes**: `ScheduledTaskTool.approveScheduledTaskRun`/`rejectScheduledTaskRun` (registered on `ScheduledTaskAgent`, with the same mandatory-confirmation instruction discipline as create/cancel — the agent must show the draft's summary and get explicit approval first); `getScheduledTaskHistory`'s run summaries now include a `summary` field (the draft text, reusing `ScheduledTaskRun.handlerResultSummary` — its doc comment was widened from "typed handler only" to also cover this). **No-history trial-run (decision #13) — closed as a same-session follow-up.** Phases 3 and 4 deferred this to "once Phase 6 lands"; once Phase 6's draft mechanism existed, this was implemented immediately after. New `service/ScheduledTaskTrialRunService.estimate(taskId, userId)` is the single entry point both `ScheduledTaskTool.trialRunScheduledTask` and `POST .../trial-run` now call: it first tries `ScheduledTaskService.trialRunEstimate` (the free historical-average path, unchanged); if that comes back unavailable (no history), it actually executes the instruction once via `AgentRunner.executeCoordinator`, in a **forced, unconditional draft/no-commit instruction** — deliberately separate from `ScheduledTaskDispatcherJob.approvalInstructionBlock`, since a trial run must never commit a real side effect regardless of the task's own `autonomyMode` (an AUTONOMOUS task's trial run must still not actually create the PO). ## Risks / Open Items to Flag to the Team

- **Notification service dependency** (Phase 5) — timeline unknown; see decision #2 for why this doesn't block release or testing.
- **One-off task completion semantics** (Phase 2, step 4) — needs a decision: does a completed one-off task stay `ACTIVE` with no future run, or transition to a terminal state distinct from `CANCELLED`?
- **Downstream service calls on behalf of a user with no live session** — confirm the business/comm service accepts system-initiated calls (dispatcher-minted service JWT + replayed userId) the same way it accepts live request-triggered calls.
- **Cron parsing accuracy** — relying on the LLM to convert phrases like "every Friday at 6pm" into a correct cron expression; recommend a validation/echo-back step (already planned in Phase 3) as the safety net rather than deterministic NLP parsing.
- **Conditional-approval threshold accuracy** (decision #11) — same class of risk as cron parsing: relying on the LLM to correctly judge an NL rule like "PO total > $500" against live run data at execution time, with no deterministic fallback. Mitigated the same way — required confirmation echo at creation (Phase 3) — but unlike cron parsing, a misjudgment here risks an unapproved side effect actually committing, not just a bad schedule. Worth flagging to the team as higher-stakes than the cron-parsing risk it parallels.
- **Best-effort task termination** (decision #12) — `AgentRunner.execute(...)` is synchronous with no cancellation hook today. Marking a run `TIMED_OUT` stops the dispatcher from waiting on it, but the underlying LLM call/tool side effects may continue executing in the background and complete (or partially commit) after the timeout was declared. The run record will say `TIMED_OUT` even if the work quietly finished. True hard-cancellation would require making `AgentRunner` interruptible — out of scope for this plan; flagging as a known limitation.
- **Token-exhaustion signal from the business service** (decision #10) — the reactive mid-run catch assumes the business service surfaces a distinguishable "exhausted" error/response; needs confirming with that team. Correction from this session's verification: `AiUsageClient.save()` is fire-and-forget, but `getOrgTokenDetails` (what the proactive pre-check actually uses) is already a blocking, synchronous call — so the *proactive* half of decision #10 (Phase 2, done) rests on firmer ground than this note originally implied. The *reactive* half remains unimplemented: Phase 2 ships proactive-only (explicit product decision this session), and a mid-run token cutoff today is indistinguishable from any other `FAILED` run — no code path tags it `TOKENS_EXHAUSTED`.
- **`coordinatorAgent`'s tenant isolation is prompt-only, with no token- or tool-level enforcement** (found while building Phase 2's `AgentRunner.executeCoordinator`) — the entire org/location scoping for this agent tree (order/inventory/purchase/retail/etc., used by every scheduled task's NL path) is a "SYSTEM CONSTRAINT" text block prepended to the prompt, trusting the LLM to obey it; there's no scoped credential or tool-level filter behind it, unlike `AgentRunner`'s MCP-based specialist-agent path. This is pre-existing behavior (identical to what live chat-stream already does), not something Phase 2 introduced — but it's arguably higher-stakes for *unattended* scheduled runs than for live chat, where a human is watching the conversation and would likely notice a scoping failure. Worth flagging to the team independent of this feature.
- **No-history trial-run still costs real tokens** (decision #13) — it's optional and free once history exists, but the first-ever trial-run on a novel instruction is a real `AgentRunner` execution with real cost. Nothing in this plan currently rate-limits repeated trial-run requests before a task has history; worth flagging to the team if abuse (e.g. spamming estimates on ever-slightly-reworded instructions) is a concern.
- **Blob output retention/lifecycle** (decision #14) — the plan stores every run's output in GCS indefinitely by default; no retention window, size cap, or deletion policy (e.g. on task cancellation) is defined yet. Needs a decision from the team before Phase 2/4 implementation, since it affects both storage cost and the cancellation soft-delete behavior in decision #7 (does cancelling a task's blobs stay retrievable forever, like the row does?).
- **Template management authorization is org-wide by default** (decision #16) — any user in the org can currently create/edit/archive templates, not just the user who created them, since the catalog check is at the `orgId` level rather than per-user. Whether template *management* (as opposed to browsing/selecting) needs role-gating (e.g. only admins/managers can define templates that others in the org will schedule tasks from) is not decided — worth a specific call from the team, since a template that's wrong or malicious affects every future task created from it, org-wide.
- ~~No-history trial-run is deferred, not built~~ — **closed 2026-08-17** via `ScheduledTaskTrialRunService`, once Phase 6's draft mechanism existed (see Phase 6's follow-up note). A brand-new task's `trialRunScheduledTask`/`POST .../trial-run` now executes once for real, in forced draft/no-commit mode, rather than returning "not available yet."
- **No per-location timezone source exists** (Phase 3) — the Data Model table says a task's `timezone` "defaults to the location's configured timezone," but nothing in this codebase resolves a location to a timezone. `ScheduledTaskService` defaults to a hardcoded `Asia/Kolkata` (matching `AgentRunner`'s own existing hardcoded anchor) when the user doesn't name one. Fine for a single-timezone deployment; will misfire for any org whose locations span timezones. Needs either a real location→timezone lookup or an explicit product decision that "always ask/confirm" is good enough.
- **Confirmation-before-persisting is prompt-only, not code-enforced** (Phase 3) — `ScheduledTaskAgent`'s instruction tells the model to echo a summary and wait for explicit confirmation before calling `createScheduledTask`/`createScheduledTaskFromTemplate`, but nothing on the server side actually gates task creation on a prior confirmation turn having happened. Same trust model already accepted for cron-phrase parsing and tenant scoping throughout this agent tree — flagging for awareness, not proposing a fix.
